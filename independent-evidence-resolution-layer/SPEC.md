# IERL v1 normative contract

## Purpose

Prevent failed, partial, missing, or model-authored material from being carried
into a later session as a verified fact.

## Resolution rule IERL-1

A claim is `VERIFIED` if and only if all of the following hold:

1. The evidence journal is parseable, hash-chain complete, and sequential.
2. The record's rule version is exactly `IERL-1`.
3. The record belongs to the run and generation being resolved.
4. The producing process identity equals the independently bound identity.
5. The event sequence is exactly `1..event_count` without gaps or duplicates.
6. The producer exit status exists and equals zero.
7. At least one required artifact is declared.
8. Every artifact is inside the declared artifact root, exists, and matches its
   declared SHA-256.
9. The claim's `value_hash` equals the verified artifact hash.
10. Every declared deterministic checker is recognized and passes.

`contains_utf8` verifies a declared canary independently of the hash check.
`json_object_keys` parses JSON and verifies all declared keys. Hash equality by
itself proves identity, not semantic correctness.

Checker selection and expected values live in a separate controller-owned
`IERL-POLICY-1` document. Evidence producers cannot choose or modify that policy.
Rules are bound to a `record_id`; a missing rule yields `UNKNOWN`. A malformed
policy is an apparatus defect. IERL-1 supports one artifact per claim; larger
artifact sets yield `UNKNOWN` until an aggregate-hash contract is specified.

Precedence is deterministic:

1. apparatus corruption -> `HARNESS_DEFECT`;
2. model-only source -> `OBSERVED`;
3. incompatible rule/scope, incomplete events, unbound identity, missing exit,
   or missing artifact -> `UNKNOWN`;
4. nonzero exit, path escape, artifact/claim hash mismatch, or checker failure
   -> `REJECTED`;
5. intact artifacts with no semantic checker -> `STORED`;
6. all requirements satisfied -> `VERIFIED`.

The resolver emits a new resolution result. It does not rewrite the evidence
record. A context view lists `VERIFIED` facts separately from non-authoritative
records. This layer does not grant permissions and does not authorize mutations.

## Fair-test requirement

Positive and adverse fixtures must use the same journal writer, resolver binary,
subprocess controller, JSON parser, comparison function, and repetition count.
Expected outcomes are static controller data; they are not generated by the
resolver. Resolver explanations are recorded but ignored by verdict comparison.

## Fail closed

Malformed controller output, malformed journal envelopes, child launch failure,
schema mismatch, or missing required result fields are `HARNESS_DEFECT`. Such a
case does not yield a target PASS or FAIL.
